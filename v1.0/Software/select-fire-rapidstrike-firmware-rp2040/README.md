# RP2040-Zero port

A port of the [v1.0 firmware](../select-fire-rapidstrike-firmware) from the Arduino Nano to a [Waveshare RP2040-Zero](https://www.waveshare.com/wiki/RP2040-Zero). Control logic is unchanged — this is a pin/board retarget, not a rewrite. See `select-fire-rapidstrike-firmware-rp2040.ino` for the ported sketch.

## Pin assignments

Digital pins keep the same number as their Nano `D` pin, just prefixed `GP`. The two analog inputs move to the RP2040's dedicated ADC-capable pins (ADC0/ADC1), since the Nano's `A0`/`A1` don't exist as such on the RP2040.

| Signal | Nano (v1.0) | RP2040-Zero | Direction | Notes |
|---|---|---|---|---|
| Trigger switch | D2 | GP2 | input | `INPUT_PULLUP`, active-low |
| High-side FET gate | D3 | GP3 | output | |
| Cycle control switch | D4 | GP4 | input | `INPUT_PULLUP`, active-low |
| Low-side FET gate / MOSFET module `TRIG/PWM` | D5 | GP5 | output (PWM) | Drives the pusher motor via PWM (see "Pusher driven by an external MOSFET module" below) |
| Fire mode — Safety | D6 | GP6 | input | `INPUT_PULLUP`, active-low; overrides everything below when grounded |
| Fire mode — Semi-auto | D7 | GP7 | input | `INPUT_PULLUP`, active-low; **required wire** for a 3-mode build |
| Fire mode — Burst fire | D8 | GP8 | input | `INPUT_PULLUP`, active-low; **required wire** for a 3-mode build |
| Fire mode — Full auto (optional) | D9 | GP9 | input | `INPUT_PULLUP`, active-low; **optional** — full auto is the default when neither GP7 nor GP8 is grounded, so this wire isn't needed unless you want all 3 non-safety positions wired explicitly. See below. |
| Pusher/solenoid select jumper | D11 | GP11 | input | `INPUT_PULLUP`; open = pusher motor, jumpered = solenoid |
| Current-sense select jumper | — (new on this port) | GP12 | input | `INPUT_PULLUP`; open = current sensing/OCP disabled, jumpered = current sensing/OCP enabled. This is about whether `CURRENT_SENSE_PIN` is actually wired to a real signal, not about whether your motor driver is an H-Bridge — see below |
| Rate-of-fire potentiometer | A0 | GP26 (ADC0) | analog input | |
| Current sense | A1 | GP27 (ADC1) | analog input | |

GP16 (the RP2040-Zero's onboard WS2812 RGB LED) and GP0/GP1 (USB) aren't used by this firmware and are free for status LEDs or other additions.

## Power input

The RP2040-Zero can be powered via VIN/VSYS at either 5V or 3.3V — 5V (e.g. off the kit's existing buck converter output, or USB) is the common choice and is fine to use. This is independent of the ADC reference: VIN/VSYS feeds an onboard regulator that always produces a regulated 3.3V rail for the RP2040 chip, and the ADC reference (`ADC_AVDD`) is tied to that regulated 3.3V rail rather than to VIN. So regardless of whether the board is fed 5V or 3.3V, `analogRead()` always scales 0–1023 to 0–3.3V.

## Board-specific firmware changes (beyond pin numbers)

- **ADC reference voltage**: `ARDUINO_SUPPLY_VOLTAGE` (5.0 on the Nano) is renamed `BOARD_SUPPLY_VOLTAGE` and set to `3.3`. This is *not* the board's power input voltage (see above) — it's the RP2040's fixed ADC reference, and it feeds directly into the current-sense math (`analogReadingToVoltage()`). It must stay `3.3` regardless of what voltage powers the board, or current-sense/OCP readings will be off by ~52% (5.0/3.3). It must also match whatever reference the current-sense circuit actually presents to the ADC pin — see the hardware caveat below.
- **ADC resolution unchanged**: the arduino-pico core's `analogRead()` defaults to 10-bit (0–1023), same as the Nano's AVR ADC, so the existing `map()`/`/1024.0` scaling in `setRateOfFire()` and `analogReadingToVoltage()` didn't need to change. If you want the RP2040's full 12-bit ADC resolution, call `analogReadResolution(12)` in `setup()` and update those two spots to divide by 4096 instead.
- **Serial init no longer blocks**: the Nano's `initSerial()` had a `while(!Serial){}` wait, which is a no-op on the Nano's always-on hardware UART. The RP2040's `Serial` is native USB CDC and only becomes truthy once a host opens the port, so that same loop would hang the blaster indefinitely with no PC attached. The port drops the wait — `Serial.begin()` still runs so `Serial.print`/`println` calls work whenever something is listening, but firing no longer depends on it.
- **Timer callback signature**: `arduino-timer`'s `Timer<>::in()`/`::every()` expect a `bool handler(void *)` callback, not a bare `bool handler()`. The Nano build only accepted the old zero-argument callbacks (`monitorCurrent`, `handleComplementaryFETTransition`, `turnOnPusherMotor`, `turnSolenoidOff`, `handleSolenoidTuronOn`) because avr-gcc's Arduino build compiles with `-fpermissive`, silently allowing the mismatched function pointer conversion. The arduino-pico core doesn't, so this is a hard compile error on RP2040 — those five handlers now take an unused `void *` parameter. No behavior change.
- **New: current-sense select jumper (GP12)**. `CURRENT_SENSE_SELECT_PIN` (originally named `H_BRIDGE_SELECT_PIN` — renamed because that name wrongly implied this was about H-Bridge vs. non-H-Bridge motor drivers, when it's really about whether `CURRENT_SENSE_PIN` is wired to a real analog current-sense signal at all; plenty of H-Bridge modules, e.g. the DRV8871, handle overcurrent protection entirely internally with nothing to wire here) gates whether the current-sense timer (and therefore OCP) is ever armed, read once in `setup()`. Open (no jumper, default HIGH) disables current sensing/OCP entirely — the correct setting whenever `CURRENT_SENSE_PIN` isn't wired to anything real, regardless of motor driver topology; jumpered (LOW) enables it, only if `CURRENT_SENSE_PIN` is actually connected to a real current-sense output. An initial version of this check had the polarity inverted (`if (digitalRead(...))` instead of `if (!digitalRead(...))`), which silently disabled OCP in exactly the jumpered configuration the feature was meant to protect — fixed before flashing. Since the pin is only read once at boot, changing the jumper requires a power cycle or reset to take effect (matches the existing `PUSHER_MECHANISM_SELECT_PIN` jumper's read-at-a-fixed-point pattern, though that one is re-read on every trigger pull rather than only at boot).
- **Fire mode selection simplified from a 4-pin exclusive scan to a 2-wire-minimum priority scheme.** The Nano/original-port design treated the 4 fire-mode pins as mutually exclusive rotary-switch positions and scanned for whichever one was grounded (`getRotSwPos()`). This port replaces that with `setCurrentFiremode()` reading pins directly in priority order: SAFETY (GP6) always overrides everything; else SEMI_AUTO if GP7 is grounded; else BURST_FIRE if GP8 is grounded; else FULL_AUTO as the true default. This means a build only needs to wire GP6 (safety) + GP7 + GP8 to get all 3 non-safety modes — full auto needs no dedicated wire. GP9 (`ROT_SW_FULL_AUTO_PIN`) still exists and is still `pinMode()`'d as `INPUT_PULLUP`, but is never read: grounding it has no effect distinct from the default, so it only matters cosmetically for builds that prefer to wire every position of a physical rotary switch explicitly.
  - **Safety-relevant consequence, confirmed intentional:** because FULL_AUTO is now an unconditional default rather than "leave the fire mode unchanged when no pin reads low," a broken/disconnected SAFETY wire (GP6 floating HIGH, same electrical state as SAFETY simply not being selected) results in FULL_AUTO on the next trigger pull rather than holding the last known mode. This was a deliberate, explicit tradeoff (confirmed when this feature was added) rather than an oversight — the original 4-pin rotary design had the same fundamental exposure (a broken common wire also grounds nothing), and there's no way to electrically distinguish "wire broke" from "you intentionally rely on the no-wire full-auto default" without adding hardware (e.g. a normally-closed safety path, or detecting the common wire independently). Worth revisiting if this board ever needs to fail toward safe on a wiring fault.
- **Cycle-control switch debounce cut to 2ms (from 50ms), and dart counting redesigned around which edge means what.** These fix a real pusher-runaway bug found and root-caused on a Nano twin of this firmware — see "Pusher driven by an external MOSFET module" below for the full story and why it has nothing to do with the RP2040 specifically. In short: the switch's contact-closure duration shrinks as motor RPM increases, and the original 50ms debounce (fine for a finger-actuated trigger) silently discarded closures shorter than that as noise — meaning at high motor speed, no cycle-control event ever registered at all, and nothing ever told the motor to stop. Fixing the debounce time surfaced a second issue: counting darts on the switch's retracted (press) edge, which happens *after* a full stroke completes, could occasionally count a stray leftover event from before the current trigger pull as "cycle complete," causing an extra shot. Darts are now counted on the released (dart-fired) edge instead, with a `dartInProgress` guard on the retracted-edge handler so it only finalizes a stop when it has a genuine matching dart-fired event to close out.
- **Pusher motor now driven via PWM, not a binary `digitalWrite()`.** A plain on/off drive gives the motor no speed control at all — it always spins at full battery voltage regardless of `rateOfFire` — which let it coast through extra cycles (and potentially fire extra darts) after being commanded to stop, since this MOSFET module has no active braking (a simple low-side switch, not a bridge) and can only cut power. `transitionLowSideFET()` now uses `analogWrite()` at `PUSHER_MOTOR_PULSE_RATE` (set once via `analogWriteFreq()` in `initFETPins()`) and a fixed `PUSHER_MOTOR_PWM_DUTY_PERCENT` duty cycle, both empirically tuned on the Nano build of this firmware (see its README). This replaces the earlier `gpio_set_drive_strength()`/`gpio_set_slew_rate()` mitigation, which was based on a hypothesis (Miller-effect self-turn-on from the onboard v1.0 schematic's FETs) that turned out not to apply to this hardware at all — see below.

## Hardware caveats (if adapting the existing v1.0 PCB rather than a new board)

These aren't firmware changes — they're things to check before wiring an RP2040-Zero into a board designed for a 5V Nano:

- **Logic level is 3.3V, not 5V.** The RP2040-Zero's GPIOs are not 5V-tolerant. Anything driving a signal into an RP2040 GPIO (rotary switch common, trigger/cycle switches) is fine as long as it's just pulling to GND against the internal pullup, which all of these are. But double-check any circuitry that was assumed to be fed 5V logic.
- **Current-sense scaling depends on the analog front-end's reference, not just the MCU's.** If the sense-resistor amplifier on the v1.0 board was scaled to present a 0–5V range to the Nano's ADC, feeding that directly into a 3.3V-max RP2040 ADC pin risks exceeding the input range. Confirm the analog front-end output swing is compatible with 3.3V before wiring it in, independent of the `BOARD_SUPPLY_VOLTAGE` firmware constant above.

## Pusher driven by an external MOSFET module instead of the onboard v1.0 FETs

A real build using this port replaces the v1.0 board's onboard pusher-drive circuitry (`Hardware/Schematics.pdf` sheet 3, "PUSHER DRIVE": Q301/Q302 FETs, the `74LVC1G07` high-side buffer) with a separate off-the-shelf module: a [High-Power Dual MOSFET Switch Module](https://protosupplies.com/product/high-power-dual-mosfet-switch-module/) (ProtoSupplies SKU MOD-117 — two AOD4184 N-channel MOSFETs in parallel as a single low-side switch, active-HIGH `TRIG/PWM` input rated 3.3–20V, accepts 5–36V DC). The only connections between the RP2040 and this module are GND and `LOW_SIDE_PIN` (GP5) driving `TRIG/PWM`; `HIGH_SIDE_PIN` (GP3) is not connected to anything in this configuration. **The pin-mapping and hardware caveats elsewhere in this README that reference the v1.0 schematic's onboard FETs do not apply to this configuration.**

### The pusher-runaway investigation

Getting this module working reliably took a long debugging session, almost entirely conducted on a Nano twin of this firmware (see `../select-fire-rapidstrike-firmware-nano-hbridge/README.md` for the blow-by-blow) rather than on the RP2040 directly, precisely because the first hypothesis was that the RP2040 itself was the problem. It wasn't. Recorded here so nobody re-treads the disproven leads.

**Symptom:** pulling the trigger at higher pack voltage (e.g. a 3S LiPo) sent the pusher into continuous "runaway" — it wouldn't stop regardless of trigger release or fire-mode switch position, and only cutting power or disconnecting the drive signal wire would stop it. Fine at lower voltage (e.g. a 5V bench supply).

**Hypotheses ruled out, each with real evidence against it — all explored on this RP2040 port before the investigation moved to the Nano:**
1. *The RP2040's 3.3V GPIO drive being insufficient for the MOSFET module's gate/trigger circuit* — either directly, or via the onboard v1.0 schematic's FETs (which this configuration doesn't even use). Disproven conclusively: the identical control logic on a **Nano at native 5V logic** exhibited the exact same runaway at high pack voltage. Logic level was never the variable, on this MCU or any other.
2. *Missing flyback diode across the inductive motor load.* A real gap (the module ships without one and its docs recommend adding one), but adding a flyback diode made no difference to the runaway.
3. *An internal pull-up on the module's `TRIG/PWM` input strong enough to overpower a bare GPIO's LOW output at higher module supply voltage.* Directly measured and disproven: with the drive wire disconnected, the module's `TRIG/PWM` pin held at ~0V even at high supply voltage. It has a real 10kΩ pull-*down*, confirmed on the physical unit.
4. *An MCU crash/brownout from motor inrush current, with the GPIO output register frozen at whatever it last wrote.* Disproven by live serial output during a runaway: the firmware kept running, correctly detecting trigger presses/releases in real time, while the pusher kept running regardless.
5. *A spurious trigger-press edge re-arming the firing sequence.* Disproven by instrumentation: diagnostic prints for every debounced trigger press/release showed an exact 1:1 match with physical trigger squeezes — no phantom presses.

**The actual root cause, confirmed by direct measurement of the cycle-control switch:** at higher motor speed, the switch's physical contact-closure duration becomes shorter than `JC_Button`'s debounce window. `JC_Button::read()` uses a re-check-after-delay debounce algorithm — it waits out the *entire* debounce time from the first detected change, then re-reads the pin, and discards the whole transition as "just noise" if the pin isn't *still* in the new state at that point. With the original 50ms debounce (fine for a finger-actuated trigger, useless for a cam that closes and reopens in single-digit milliseconds at speed), **zero cycle-control events registered at high motor speed at all** — confirmed directly via a live serial log during a runaway. Since every stop-or-continue decision in `handlePusherMotorFiring()` lived inside the cycle-control event handler, nothing ever told the motor to stop.

Fixing that (cutting the debounce to 2ms) immediately fixed full-auto, but surfaced two more real, distinct problems:

- **Extra shots on semi-auto/burst.** Counting darts on the switch's *retracted* (press) edge — which happens after a full stroke completes — meant a stray retracted-event carried over from before the current trigger pull (e.g. the pusher hadn't fully settled home yet) could be misread as "cycle done, still need more darts, fire again." Fixed by counting darts on the *released* (dart-fired) edge instead, gated by the `dartInProgress` flag on the retracted-edge handler.
- **Motor coasting through extra cycles after the commanded stop.** This module is a simple low-side switch with no high-side FET — there is no way to actively brake or short the motor, only cut power. A motor driven at full battery voltage via plain on/off switching has enough momentum to coast through one or more additional complete pusher strokes after being told to stop, which can mechanically fire additional darts independent of anything the firmware decided. Fixed by adding real PWM speed control (`PUSHER_MOTOR_PULSE_RATE`/`PUSHER_MOTOR_PWM_DUTY_PERCENT`, via `analogWriteFreq()`/`analogWrite()`) and empirically reducing motor speed until coasting no longer reached another full stroke — tuned on the Nano build at `PUSHER_MOTOR_PWM_DUTY_PERCENT=45`, which will need re-verifying (and likely re-tuning) on this RP2040 build with real hardware, since it hasn't been field-tested here yet (see "Build/flash status" below).

None of this was ever about the RP2040 being individually at fault — it was a debounce time tuned for a human finger applied to a cam switch, dart-counting keyed to the wrong edge, and a control topology (single low-side switch) with no active braking that a binary on/off drive couldn't compensate for. All three apply equally to any MCU driving this module.

## Dependencies

Same Arduino libraries as the Nano firmware (Library Manager): `JC_Button`, `CircularBuffer`, `arduino-timer`. Board support: install the [earlephilhower/arduino-pico](https://github.com/earlephilhower/arduino-pico) core via Boards Manager ("Raspberry Pi Pico/RP2040"), then select the "Waveshare RP2040 Zero" board.

Note: `#include <CircularBuffer.h>` prints a deprecation pragma on recent releases of that library; this sketch includes `<CircularBuffer.hpp>` instead, which is silent and behaves identically.

## Build/flash status

Compiled clean (no warnings) and flashed to a physical Waveshare RP2040-Zero via `arduino-cli` using:

- Core: `rp2040:rp2040` 5.6.1 (`earlephilhower/arduino-pico`), board `rp2040:rp2040:waveshare_rp2040_zero`
- Libraries: `JC_Button` 2.1.6, `CircularBuffer` 1.4.0, `arduino-timer` 3.0.1

Flashing: hold BOOTSEL while plugging in (or double-tap the reset button on an already-running board) to expose the `RPI-RP2` USB mass-storage drive, then copy the built `.uf2` file onto it — the board reboots into the new firmware automatically.

After flashing, the board came up correctly (rotary switch, trigger, and cycle-control pins init fine; `arduino-timer` callbacks fire; USB serial works). Before the H-Bridge select jumper (GP12) was added, with nothing wired to the current-sense pin (GP27) it continuously printed `OCP`, since a floating ADC pin combined with the 0.01Ω sense-resistor math reads as spurious high current. After adding the jumper (and fixing its inverted polarity), current sensing/OCP is disabled by default with no jumper on GP12, so the bare dev board no longer prints `OCP` — that spam would only reappear now with the GP12 jumper installed and nothing wired to GP27.

Re-flashed via `arduino-cli upload -p /dev/ttyACM0 --fqbn rp2040:rp2040:waveshare_rp2040_zero`, which auto-resets an already-running board into BOOTSEL over USB (1200bps touch) — no physical BOOTSEL/reset button press needed for boards already running earlier RP2040 firmware from this repo.

Re-flashed again after the fire-mode selection simplification above; compiled clean and the board came back up stable (verified over several seconds of USB re-enumeration checks, no crash/reboot loop).

Re-flashed again after adding the `gpio_set_drive_strength()`/`gpio_set_slew_rate()` mitigation for the 12V-pack pusher runaway (since superseded — see below).

**Ported the confirmed fix from the Nano build** (cycle-control debounce/edge-counting redesign, PWM motor speed control, removal of the now-disproven `gpio_set_drive_strength()`/`gpio_set_slew_rate()` mitigation) and recompiled clean (`rp2040:rp2040` 5.6.1, board `waveshare_rp2040_zero`) — but **this has not yet been flashed to or field-tested on a physical RP2040-Zero**, since the board wasn't connected when this port was done. The underlying fix is proven correct on a Nano running byte-for-byte equivalent logic against real hardware (3S LiPo + MOD-117 module, all three non-safety fire modes confirmed working with no runaway or extra shots — see `../select-fire-rapidstrike-firmware-nano-hbridge/README.md`), but that doesn't substitute for verifying this specific board/toolchain combination. Flash and field-test before relying on this build.

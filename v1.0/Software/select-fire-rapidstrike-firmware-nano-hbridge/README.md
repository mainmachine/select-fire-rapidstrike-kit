# Nano + H-Bridge motor driver build

An Arduino Nano build of the v1.0 select-fire firmware, driving the pusher motor through an external **DRV8871-based H-Bridge motor driver module** (e.g. [Adafruit's DRV8871 DC Motor Driver Breakout](https://www.adafruit.com/product/3190), 6.5–45V, current-limiting adjustable via an `Rlim` resistor — 2A stock, up to 3.6A modified) instead of the v1.0 board's onboard half-bridge FETs (`Hardware/Schematics.pdf` sheet 3, "PUSHER DRIVE").

This firmware started life as a diagnostic sketch (`Software/tests/nano-5v-drive-test/`) used to rule out whether the [RP2040 port](../select-fire-rapidstrike-firmware-rp2040)'s 3.3V logic was the cause of a pusher-runaway bug, at which point it drove a single low-side MOSFET switch module (ProtoSupplies MOD-117) instead of an H-Bridge. It wasn't the RP2040's logic level — the real causes turned out to be more fundamental (see "The pusher-runaway investigation" below) and applied equally to a 5V Nano, so this became a real firmware build in its own right rather than a throwaway test. It was later switched from the MOD-117 to this DRV8871-based H-Bridge specifically to get real active braking, since the MOD-117 (a simple low-side switch with no high-side FET) couldn't brake at all — see "Switching to an H-Bridge" below.

## Pin assignments

| Signal | Nano pin | Direction | Notes |
|---|---|---|---|
| Trigger switch | D2 | input | `INPUT_PULLUP`, active-low |
| Current-sense select jumper | D3 | input | `INPUT_PULLUP`; open = current sensing/OCP disabled, jumpered = enabled. **Leave this open** with the DRV8871 — see "Current sensing" below |
| Cycle control switch | D4 | input | `INPUT_PULLUP`, active-low; wired **closed when the pusher is fully retracted** — see below |
| Fire mode — Safety | D6 | input | `INPUT_PULLUP`, active-low; overrides everything below when grounded |
| Fire mode — Semi-auto | D7 | input | `INPUT_PULLUP`, active-low; required wire for a 3-mode build |
| Fire mode — Burst fire | D8 | input | `INPUT_PULLUP`, active-low; required wire for a 3-mode build |
| Fire mode — Full auto (optional) | D9 | input | `INPUT_PULLUP`, active-low; optional — full auto is the default when neither D7 nor D8 is grounded |
| `LOW_SIDE_PIN` / H-Bridge `IN1` | **D10** | output (PWM) | The pin that's actually PWM'd, via Timer1/OC1B — see "Why D10, not D11" below. Despite the macro name, this drives the DRV8871's `IN1`, not `IN2` |
| `HIGH_SIDE_PIN` / H-Bridge `IN2` | **D11** | output | Held fixed HIGH while driving or braking, LOW only when fully off — **not** PWM'd. Despite the macro name, this drives the DRV8871's `IN2`, not `IN1` — see "Switching to an H-Bridge" below |
| Pusher/solenoid select jumper | D12 | input | `INPUT_PULLUP`; open = pusher motor, jumpered = solenoid |
| Rate-of-fire potentiometer | A0 | analog input | |
| Current sense | A1 | analog input | Unconnected/unused with the DRV8871 — it handles overcurrent protection internally with no exposed sense signal |

`HIGH_SIDE_PIN`, `PUSHER_MECHANISM_SELECT_PIN`, and `CURRENT_SENSE_SELECT_PIN` moved from their original D3/D11/D12 assignments (D3=high-side, D11=pusher-mechanism, D12=current-sense) to D11/D12/D3 respectively, to free up D11 (a PWM-capable pin, Timer2/OC2A) in case it ended up being the one that needed PWM — it didn't (see "Why D10, not D11" below), but the pin move stuck. **The macro names no longer match the DRV8871's `IN1`/`IN2` labels at all** — confirmed against the actual physical wiring, `LOW_SIDE_PIN` (D10) drives `IN1` and `HIGH_SIDE_PIN` (D11) drives `IN2`, the reverse of what the names imply. Watch for this if comparing against an older wiring diagram or a build using earlier pin numbers.

The H-Bridge module's `VM`/`GND` connect to the pack/motor supply (not the Nano's logic supply), and its two-pin `OUT` terminal block goes to the pusher motor. `GND` is common with the Nano.

## Switching to an H-Bridge

The original MOD-117-based design (see "The pusher-runaway investigation" below) needed a substantially reduced PWM duty cycle just to keep the pusher motor's coasting momentum from carrying it through extra, mis-firing cycles after being commanded to stop — because that module is a single low-side switch with no high-side FET, so it can only cut power, never actively brake. That made the blaster noticeably sluggish. A real H-Bridge (this DRV8871 module) can short the motor terminals together on command for genuine active braking, which arrests the pusher's momentum far more effectively than passive coasting ever could — confirmed on actual hardware at the datasheet's suggested 50% starting point. Raising `PUSHER_MOTOR_PWM_DUTY_PERCENT` to 70% for more speed initially surfaced a *different* bug (inconsistent firing, pusher not always reaching retracted) — not a coasting/extra-shot problem, but an edge-only drive/brake decision that couldn't recover from timing slop at the faster pusher speed. See "Ensuring full retraction: level-based drive, not edge-triggered" below for the fix.

This is **not a drop-in pin relabeling** — the DRV8871's control logic is fundamentally different from the discrete P-channel-high/N-channel-low FET pair this firmware's `transitionHighSideFET()`/`setFETsForBraking()` were originally written for, and getting this wrong is actively dangerous (it can drive the motor continuously while the firmware believes it's idle). The DRV8871's truth table, confirmed against TI's datasheet (SLVSCY9B, Table 1, "H-Bridge Control," page 8) and against the actual physical wiring — `IN1`=`LOW_SIDE_PIN` (D10), `IN2`=`HIGH_SIDE_PIN` (D11):

| IN1 | IN2 | Result |
|---|---|---|
| 1 | 0 | Drive (direction depends on wiring — swap the two motor leads on the `OUT` terminal block if it's backwards; the direction label itself is arbitrary for a pusher) |
| 0 | 1 | Drive (other direction) |
| 0 | 0 | **Coast** (both outputs floating) |
| 1 | 1 | **Brake** (motor terminals shorted — real active braking) |

Per the datasheet's recommended PWM technique (page 8: "it typically works best to switch between driving and braking... IN1 = 1 and IN2 = 0 during the driving period, and IN1 = 1 and IN2 = 1 during the other period"), one input is held fixed HIGH throughout driving *and* braking, and only the other actually toggles/PWMs. The datasheet's own worked example fixes `IN1` and PWMs `IN2` — but motor direction is irrelevant for this cam-driven pusher (drive polarity only decides which way the motor spins, and a cam-driven pusher's stroke doesn't care), so this firmware swaps the roles: `IN2` (`HIGH_SIDE_PIN`/D11) is the fixed pin, and `IN1` (`LOW_SIDE_PIN`/D10) is the one that's PWM'd. This is deliberate, not arbitrary: it puts the PWM on D10/Timer1 (a 16-bit timer that hits an exact target frequency) instead of D11/Timer2 (an 8-bit timer limited to fixed prescaler steps) — see "Why D10, not D11" below.

Firmware changes needed to match this, all a direct consequence of the original code assuming a different FET topology and, initially, a wrong guess at which macro mapped to which physical `IN` pin:

- **`transitionHighSideFET()` (drives `IN2`/D11) no longer inverts its output**, and is a plain `digitalWrite()`, never PWM'd. The original half-bridge code inverted its high-side pin because the onboard v1.0 board's high-side FET was P-channel and needed its gate pulled *low* to turn on — the DRV8871's `IN2` is a plain active-high logic input needing no inversion. It's driven HIGH for both "on" and "brake" (fixed, per the datasheet technique above) and LOW only when fully off (coast).
- **`transitionLowSideFET()` (drives `IN1`/D10) now sets `OCR1B` directly** (`0`=solid LOW/off, `PUSHER_MOTOR_PWM_TOP+1`=solid HIGH/brake, via the "set above TOP" trick) instead of `digitalWrite()`, since this pin is under Timer1 PWM control. `setFETsForBraking()` sets it fully HIGH (matching the `(1,1)`=brake convention above) rather than the old "high-side on, low-side off" pattern that made sense for a single P-channel FET shorting a motor terminal to the battery rail, but means nothing to a full H-Bridge.
- **`driveDrv8871PWM()` (replacing the old `driveLowSidePWM()`) PWMs `IN1`/D10** between LOW (driving) and HIGH (braking/slow decay) at `PUSHER_MOTOR_PWM_DUTY_PERCENT`, used only for the actual "on"/firing state, never for braking — braking needs `IN1` held solidly HIGH via `transitionLowSideFET()`, not PWM'd through `driveDrv8871PWM()`; PWM'ing what's supposed to be a continuous brake signal would leave `IN1` low part of the time, which isn't braking, it's an intermittent unwanted drive pulse every cycle.

An earlier version of this firmware had `LOW_SIDE_PIN`/`HIGH_SIDE_PIN` swapped relative to the actual board — i.e. assumed `HIGH_SIDE_PIN`=`IN1`, `LOW_SIDE_PIN`=`IN2` — which silently drove the wrong physical pin with PWM and held the wrong pin fixed, and was the reason the pusher mechanism didn't work at all on first bring-up with this module. A subsequent version corrected the mapping but PWM'd `IN2`/D11 (via Timer2) per the datasheet's own literal worked example, before it was pointed out that direction doesn't matter here and the PWM could instead land on `IN1`/D10 (via Timer1) for an exact target frequency — the current version. Always verify macro-to-`IN`-pin mapping against the actual wiring, not the macro names, before trusting this section.

The existing shoot-through-delay timer between FET-state transitions (`SHOOT_THROUGH_DELAY`, `hasComplementaryTransitionBegun`) is no longer strictly necessary — the DRV8871 has its own internal dead-time protection between its own high/low-side FET pairs — but it's harmless to leave in place; it just adds a small, fixed ~1ms delay before each commanded state change takes effect.

## Ensuring full retraction: level-based drive, not edge-triggered

One dart-firing cycle is: pusher motor engaged (`ON`) until the cycle-control switch opens, then engaged until it closes again — closing is the only reliable signal that the pusher has actually reached fully retracted. Braking must only ever be committed once the switch is confirmed closed; while it's open, the motor must be driven, full stop, no exceptions.

At `PUSHER_MOTOR_PWM_DUTY_PERCENT=70` (see "Switching to an H-Bridge" above), the pusher intermittently stopped mid-stroke instead of reaching retracted, and firing became inconsistent — this didn't happen at 50%. The root cause: `handlePusherMotorFiring()` only ever *set* `targetPusherState=ON` in response to specific edges (a fresh trigger pull, or the delayed timer callback that restarts the motor between shots in a burst/full-auto sequence) and otherwise trusted that nothing else would touch it until the switch's confirmed-closed edge fired. Nothing continuously re-checked "are we still supposed to be driving?" while the switch was still open — so any brake/off command that landed prematurely (nothing else in this firmware currently emits one while genuinely firing, but this held true even so) had no way to be corrected before the next real cycle, since the only way `targetPusherState` was reasserted was by those same one-shot edges. Faster pusher travel at higher duty cycle made any timing slop far more consequential.

Fixed by making the invariant an explicit, continuous **level** check rather than an edge reaction: `handlePusherMotorFiring()` now re-asserts `targetPusherState=ON` on *every single call* whenever firing is active outside of safety mode and the cycle-control switch currently reads open. This is a no-op in the normal case (the state is already `ON`), so it doesn't interfere with the intentional brake-then-delayed-restart pause between shots in a burst (during which the switch reads closed the entire time, so the check never fires) — it only ever matters in the case it exists to prevent: something leaving the pusher un-driven while it's still mid-stroke. Braking itself is still only ever committed on the switch's debounced closed edge (`wasCycCtrlSwPressed`), unchanged.

## Serial baud rate: 115200, not 9600

After the level-based drive fix above, firing at `PUSHER_MOTOR_PWM_DUTY_PERCENT=70` still stuttered — a real, physically-felt hesitation, not just a logging artifact. A closer look at the serial log showed stroke durations (time between a dart-fired and the next retracted event) alternating almost exactly between two values roughly 50ms apart, cycle after cycle — too regular to be mechanical variation.

The actual cause: this firmware's diagnostics print substantial text right at the events that also drive FET-transition timing — `[dartFired] mode=... darts=.../... stopAfterThisCycle=...` and similar lines run 40-60+ bytes. At the original 9600 baud, a single such line takes on the order of 50ms to transmit. The AVR's 64-byte hardware TX buffer fills faster than it drains at that rate, and once full, `Serial.print()`/`println()` busy-wait for space — blocking `loop()` entirely, including `fetState.shootThroughProtectionTimer.tick()`, the timer that actually re-engages the motor (transitions it from the brief commanded OFF/coast back to `ON` or `BRAKE`) after `SHOOT_THROUGH_DELAY`. A designed ~1ms gap became however long the blocked print happened to take — sometimes tens of milliseconds — which is exactly what a "stutter" feels like on the actual hardware. This wasn't specific to the DRV8871 or to 70% duty; it was always present, just not consequential until cycle timing got tight enough for a single blocked print to matter.

Fixed by raising `Serial.begin()` in `initSerial()` from 9600 to 115200 — over 10x faster per byte, making each diagnostic line's transmit time negligible against the timers it was previously delaying. **The serial monitor/terminal must be reconnected at 115200 baud to read this firmware's output correctly** — 9600 will show garbled text.

## Current sensing

The current-sense select jumper (D3) was originally named/documented as "for H-Bridge configurations," which is actively misleading now: it's really about whether `CURRENT_SENSE_PIN` (A1) is wired to a real analog current-sense signal, completely independent of whether your motor driver is an H-Bridge. The DRV8871 handles overcurrent protection entirely internally (current-limiting via its `Rlim` resistor, thermal shutdown) with **no exposed current-sense output** — so `CURRENT_SENSE_PIN` stays unconnected, and this jumper must stay **open** (disabled). Jumpering it with nothing wired to A1 would arm `monitorCurrent()` against a floating ADC pin, and floating-pin noise reads as spurious high current — the firmware would falsely trip its own software OCP.

## Why D10, not D11

The DRV8871 datasheet's recommended PWM technique (see "Switching to an H-Bridge" above) holds one input fixed while the other does the actual switching, and its own worked example fixes `IN1` and PWMs `IN2` — which on this board's physical wiring would put the PWM on `IN2`=`HIGH_SIDE_PIN` (D11). But that example only fixes `IN1` because the datasheet is written for a generic motor where drive direction matters; for this cam-driven pusher, direction is irrelevant (a cam-driven stroke works the same regardless of which way the motor spins), so either input can be the fixed one. This firmware fixes `IN2`=`HIGH_SIDE_PIN` (D11) instead and PWMs `IN1`=`LOW_SIDE_PIN` (D10), specifically to land the PWM on a timer that can hit an exact target frequency.

D10 uses **Timer1**, a 16-bit timer with a freely adjustable `ICR1`-as-TOP, so it can hit an exact target frequency (see `PUSHER_MOTOR_PULSE_RATE`, currently 15kHz) — unlike D11's **Timer2**, an 8-bit timer with a fixed 256-count period in its Phase-Correct PWM mode, limited to fixed prescaler steps (~31.25kHz, ~3.9kHz, etc., none of which land on 15kHz exactly). Timer1 is otherwise unused in this sketch and completely independent of `millis()`/`micros()` (unlike D5/D6's **Timer0**, which the Arduino core also uses to drive `millis()`/`micros()` — reconfiguring it would corrupt timekeeping for `arduino-timer`, which schedules every delayed action in this firmware, and for `JC_Button`'s debounce logic). See `initFETPins()` for the register setup (Fast PWM, mode 14, `ICR1` as TOP, prescaler 1) and `PUSHER_MOTOR_PULSE_RATE`/`PUSHER_MOTOR_PWM_TOP`/`PUSHER_MOTOR_PWM_BRAKE_LEVEL` for how the frequency and duty cycle are derived.

## The pusher-runaway investigation (historical — MOD-117 hardware, since replaced)

**This entire section describes the ProtoSupplies MOD-117 single-MOSFET module this build no longer uses by default** (see "Switching to an H-Bridge" above). It's kept because the debounce-time, edge-counting, and PWM-speed-control design choices it produced are still exactly what this firmware does today, and because the disproven hypotheses are worth not re-treading if a future hardware change resurfaces similar symptoms. It does *not* describe the current DRV8871-based build's behavior or problems.

This section exists because getting here took a long debugging session, and the eventual cause was completely different from where the investigation started.

**Symptom:** with the pusher motor driven through the MOD-117 module, pulling the trigger at higher pack voltage (e.g. a 3S LiPo) would send the pusher into continuous "runaway" — it wouldn't stop regardless of trigger release or fire-mode switch position, and only cutting power or disconnecting the drive signal wire would stop it. It worked fine at lower voltage (e.g. 5V bench supply).

**Hypotheses ruled out, in the order tried, each with real evidence against it:**
1. *RP2040's 3.3V GPIO drive being insufficient for the MOSFET module's gate/trigger circuit.* Disproven by this very firmware: the exact same control logic on a **Nano at native 5V logic** exhibited the identical runaway at high pack voltage. Logic level was never the variable.
2. *Missing flyback diode across the inductive motor load.* A real gap (the module ships without one and its docs recommend adding one), but adding a flyback diode made no difference to the runaway.
3. *An internal pull-up on the module's `TRIG/PWM` input strong enough to overpower a bare GPIO's LOW output at higher module supply voltage.* Directly measured and disproven: with the drive wire disconnected, the module's `TRIG/PWM` pin held at ~0V even at high supply voltage. It has a real 10kΩ pull-*down*, confirmed on the physical unit — the opposite of what would cause this symptom.
4. *An MCU crash/brownout from motor inrush current, with the GPIO output register frozen at whatever it last wrote.* Disproven by live serial output during a runaway: the firmware kept running, correctly detecting trigger presses/releases in real time (verified via diagnostic prints), while the pusher kept running regardless.
5. *A spurious trigger-press edge re-arming the firing sequence.* Disproven by instrumentation: `TRIGGER PRESSED (new edge)`/`TRIGGER RELEASED` diagnostic prints showed an exact 1:1 match with physical trigger squeezes — no phantom presses.

**The actual root cause, confirmed by direct measurement of the cycle-control switch:** at higher motor speed, the cycle-control switch's physical contact-closure duration becomes shorter than `JC_Button`'s debounce window. `JC_Button::read()` uses a re-check-after-delay debounce algorithm — it waits out the *entire* debounce time from the first detected change, then re-reads the pin, and discards the whole transition as "just noise" if the pin isn't *still* in the new state at that point. With the original 50ms debounce time (fine for a finger-actuated trigger, useless for a cam that closes and reopens in single-digit milliseconds at speed), **zero cycle-control events registered at high motor speed at all** — confirmed directly: a live serial log during a runaway showed no `CYC CTRL PRESSED`/`RELEASED` events whatsoever until the motor had slowed enough (while cutting power) for one closure to finally last the full debounce window. Since every stop-or-continue decision in `handlePusherMotorFiring()` lived inside the cycle-control event handler, nothing ever told the motor to stop.

Fixing that (cutting `cycCtrlSw`'s debounce to 2ms) immediately fixed full-auto and stopped the indefinite runaway, but surfaced two more real, distinct problems, both addressed by the design described in the file header and struct comments:

- **Extra shots on semi-auto/burst.** Counting darts on the switch's *retracted* (press) edge — which happens after a full stroke completes — meant a stray retracted-event carried over from before the current trigger pull (e.g. the pusher hadn't fully settled home yet) could be misread as "cycle done, still need more darts, fire again." Fixed by counting darts on the *released* (dart-fired) edge instead, and gating the retracted-edge handler on `dartInProgress` so it only acts when it has a genuine matching dart-fired event to close out.
- **Motor coasting through extra cycles after the commanded stop.** The MOD-117 module is a simple low-side switch with no high-side FET — there is no way to actively brake or short the motor, only cut power. A motor driven at full battery voltage via plain on/off switching has enough momentum to coast through one or more additional complete pusher strokes after being told to stop, which can mechanically fire additional darts independent of anything the firmware decided. Fixed by adding real PWM speed control (see "Why D10, not D11" above) and empirically reducing motor speed until the coasting distance no longer reached another full stroke. `PUSHER_MOTOR_PWM_DUTY_PERCENT` was tuned on the actual hardware: 50% eliminated the multi-cycle runaway but still coasted through one extra stroke; 30–45% eliminated the extra shots entirely, with 45% chosen as the fastest value that still tested clean. This will need re-tuning for a different motor or battery voltage.

None of this was about the RP2040, the Nano, or the MOSFET module being individually at fault — it was a combination of a debounce time tuned for a human finger applied to a cam switch, dart-counting keyed to the wrong edge, and a control topology (single low-side switch) with no active braking that a binary on/off drive couldn't compensate for.

## Build/flash status

**MOD-117 configuration:** compiled and flashed via `arduino-cli` (`arduino:avr:nano:cpu=atmega328`) to a physical Nano, and field-verified on the actual hardware (3S LiPo + MOD-117 module) through the debugging process above: semi-auto, burst, and full-auto all confirmed working correctly with no runaway or extra shots at `PUSHER_MOTOR_PWM_DUTY_PERCENT=45`.

**DRV8871 configuration:** the `transitionHighSideFET()`/`setFETsForBraking()`/`driveLowSidePWM()` changes and the `CURRENT_SENSE_SELECT_PIN` rename compile clean. This directory was also renamed from `select-fire-rapidstrike-firmware-nano-mosfet-module` to reflect the DRV8871 H-Bridge now being the default hardware.

`HIGH_SIDE_PIN` was subsequently moved from D3 to D11, and `PUSHER_MECHANISM_SELECT_PIN` from D11 to D12 — which collided with `CURRENT_SENSE_SELECT_PIN`, already on D12 from the earlier rename. Both pins can't share one jumper without unintentionally coupling "solenoid vs. pusher motor" and "current-sense enable" together. `CURRENT_SENSE_SELECT_PIN` was moved to D3 (freed up by the `HIGH_SIDE_PIN` move) to resolve this — see the pin table above for the current, correct assignments.

That pin move initially shipped with an incorrect `IN1`/`IN2` assumption (`HIGH_SIDE_PIN`=`IN1`, `LOW_SIDE_PIN`=`IN2`) — the pusher mechanism didn't move at all as a result, since the firmware was PWM'ing the pin the datasheet says to hold fixed, and holding fixed the pin that needs to PWM. First corrected against the actual physical wiring (`LOW_SIDE_PIN`(D10)=`IN1`, `HIGH_SIDE_PIN`(D11)=`IN2`) by moving PWM generation to Timer2/D11 (`~31.25kHz`), following TI's documented technique literally (fix `IN1`, PWM `IN2`). Since motor direction is irrelevant for this cam-driven pusher, PWM generation was then moved back to Timer1/D10 instead (`transitionLowSideFET()`/`driveDrv8871PWM()` now drive `OCR1B`, `transitionHighSideFET()` is a plain `digitalWrite()` on D11) so the exact 15kHz frequency could be restored, rather than being limited to Timer2's fixed prescaler steps. Starting duty cycle set to 50% per the datasheet's suggested starting point — see "Switching to an H-Bridge" and "Why D10, not D11" above. **Confirmed working on actual hardware at 50%.** Raising to 70% initially caused inconsistent firing and intermittent failure to reach fully retracted, root-caused to an edge-only (rather than continuous, level-based) drive/brake decision — fixed per "Ensuring full retraction: level-based drive, not edge-triggered" above. That fix alone left a real physical stutter at 70%, traced to `Serial.print()` at 9600 baud blocking `loop()` (and the FET-transition timer it drives) long enough to matter — fixed by raising the baud rate to 115200, per "Serial baud rate: 115200, not 9600" above. **Confirmed working on actual hardware at 70%** with both fixes in place. Raised further to `PUSHER_MOTOR_PWM_DUTY_PERCENT=90` for more speed; compiled clean and reflashed, awaiting field re-test (**remember to reconnect your serial monitor at 115200**).
